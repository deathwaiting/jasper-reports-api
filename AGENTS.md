# AGENTS.md

Spring Boot 4.1.1 REST service (Java 25, Maven wrapper) that generates JasperReports 7.0.8 from JRXML files on disk. Virtual threads are enabled (`spring.threads.virtual.enabled=true`).

## Commands
- Build/test: `./mvnw test` (use `./mvnw`, not `mvn`). All 11 tests are `@SpringBootTest` integration tests.
- Single test class: `./mvnw test -Dtest=GetJdbcReportTest`
- Dev server: `./mvnw spring-boot:run -Dspring-boot.run.profiles=dev` — H2 in-memory, security disabled, serves `src/test/resources/test-reports`. Profile `localdev` additionally enables the admin API.
- Stress test: `bin/stress.sh` (optional, opt-in) — clean-installs the application (`./mvnw clean install -DskipTests`), builds the stress jar (`./mvnw -Pstress-test package -DskipTests`), boots it with `java -jar --spring.profiles.active=stress-test`, runs the Gatling simulation from the standalone `stress-sim/` module, and ALWAYS kills the app afterwards via an `EXIT` trap (works on failed assertions AND Ctrl-C). Run just Gatling against a live server with `./mvnw -f stress-sim/pom.xml gatling:test -Dstress.base.url=http://host:port`. Gatling reports land in `stress-sim/target/gatling/`; the app logs go to `target/stress-app.log` (pid in `target/stress-app.pid`).
- Docker image (two-step, must run together): `./mvnw clean spring-boot:build-image docker:build` — first builds `:temp`, docker-maven-plugin retags to `${project.version}`.

## Tests
- No external DB needed: embedded H2 is auto-configured (H2 and many JDBC drivers are on the classpath; H2 wins for embedded use).
- Fonts are required at runtime for Jasper even if unused — on minimal systems install `fontconfig`/`ttf-dejavu` before `./mvnw test` (CI installs `freetype-dev fontconfig-dev ttf-dejavu`; Dockerfile installs `fontconfig fonts-dejavu-core`).
- `AdminApiTest` asserts the exact list of 6 `.jrxml` fixtures under `src/test/resources/test-reports` — adding/renaming a fixture file there breaks it.
- Fixture format: all committed `.jrxml` (incl. the two main reports `sub-report/report.jrxml`, `book/book.jrxml`) are JR 7.0.8's namespace-less Jackson format — root `<jasperReport>` has no `xmlns`, elements are `<element kind="staticText|textField|image|subreport|...">`, parts are `<part><component kind="subreportPart">...</component></part>`, and true/false attributes use `forPrompting`/`titleNewPage`/`bold` (NOT `isForPrompting`/`isTitleNewPage`/`isBold`). Jaspersoft Studio 6.x emits the old schema/namespace format, which JR 7 cannot parse (`detectReportXML=false` → "Unable to load report"); the old `isForPrompting` etc. attribute names are outright rejected by the Jackson reader. Generate new fixtures with the JR 7 writer (`JacksonReportWriterFactory`) or hand-write against the samples in `demo/samples` (e.g. `FirstJasper.jrxml`) of the TIBCOSoftware/jasperreports repo.
- JR 7 `Caffeine`-compiled `.jasper` files are NOT wire-compatible with 6.x ones (`InvalidClassException` on `JRBaseReport.columnCount`) — deprecated old-era committed binaries were recompiled with 7.0.8.
- `GetJdbcReportTest`/`AdminApiTest` run under the default profile and hit endpoints with HTTP Basic auth `user`/`pass` (`src/test/resources/application-default.properties`). `SecurityOffTest` overrides with the `security-off` profile.
- Passing tests write generated reports to temp files and log the path — these are side artifacts, not assertions.

## Config quirks
- Cache TTL/size keys have a duplicated-prefix typo that is loaded and documented everywhere — use exactly `dev.galal.dev.galal.jasper-rest-server.reports.cache.ttl` / `.size` (see `CacheConfig.java` and `application.properties`). All other keys use the sane `dev.galal.jasper-rest-server.*` prefix (e.g. `reports-dir`, `admin.api.enabled`). Do not "fix" the typo without updating `CacheConfig`, `application.properties`, and README together. Note the `dev.galal.jasper-rest-server.reports.cache.ttl` key that `application.properties`/README declare (TTL, no doubled prefix) is dead — `CacheConfig` always reads the typo'd key and falls back to 1440.
- Admin API is `GET /admin/server/info`, disabled by default; gate with `dev.galal.jasper-rest-server.admin.api.enabled=true`.

## Architecture / API
- `GET /report/<relative-path>.<ext>` serves any JRXML under `reports-dir` (default `/var/reports`). Supported extensions: `pdf`, `docx`, `xlsx`, `html`, `csv`; the `.jrxml` path is derived by swapping the extension, so nested subdirs work. Unknown extension or missing file → 406 with a ProblemDetail whose `detail` is resolved from `messages.properties` (`error.report.*`).
- All query params are passed as report parameters and parsed to Java types by declared parameter class (see `JRParameterParser`). Passing a param not declared in the report throws. `JR_force_compile=true` recompiles sub-reports from their `.jrxml` into sibling `.jasper` files on disk, so the reports dir must be writable when it's used.
- The `sub-report/` and `book/` fixtures reference sibling `.jasper` files via `<subreportExpression>` (e.g. `./emp-report.jasper`), and both the `.jrxml` and `.jasper` are committed — Jasper loads the `.jasper` at fill time. `JR_force_compile=true` is what regenerates those `.jasper` files from the `.jrxml`. Adding a sub-report fixture means also shipping a matching `.jasper` sibling.
- Flow: `ReportController` → `JdbcReportGeneratorService` (compile-or-cache via Caffeine cache `reports`, fill with `JRFiller` + JDBC connection) → format exporter in `ReportHandlers`.
- Compiled `JasperReport`s are cached in-memory (Caffeine); cache is keyed by requested report path. Sub-reports use relative resource resolution (compile-time and via `JRFiller` context), so fixtures reference sibling files.
- Security: default profile uses Spring's in-memory basic auth (`spring.security.user.*`); profiles `dev` and `security-off` disable it (`DevProfileSecurity`). `DevProfileSecurity` uses `PathPatternRequestMatcher.pathPattern("/**")` — Spring Security 7 removed `AntPathRequestMatcher`, don't reintroduce it.
- The `AppError` 406 ProblemDetail explicitly sets `type=about:blank` (`AppError.java`) because Spring Boot 4 omits the `type` field when unset; `GetJdbcReportTest` asserts it.
- Dependency pins forced by the Boot 4.1.1 upgrade: `rest-assured` is pinned to **6.0.1** (Boot 4's BOM stopped managing it; 5.5.x dies with a Groovy NPE because `jasperreports-groovy` pulls Groovy 5 on the compile classpath); `jasperreports-spring` is excluded from the JR module set (pins Spring 6.2.19, clashes with Boot 4's Spring 7.x) and with it `jasperreports-chart-themes` (its `jasperreports_extension.properties` hard-requires `net.sf.jasperreports.spring.SpringExtensionsRegistryFactory` → `ClassNotFoundException` at runtime). Full exclusion rationale is a comment in `pom.xml`.
- Virtual threads: `spring.threads.virtual.enabled=true` in `application.properties`; keep it — Jasper fills are thread-safe per fill context.
- Docker `ENTRYPOINT` puts `/var/reports` on the classpath so font jars/other report resources placed there are loadable.
- In the Docker image, install `libfreetype6-dev fontconfig fonts-dejavu-core` — the image fails to generate reports without them.
- `.gitlab-ci.yml` only runs a `dockerize` stage (no tests in CI). There is deliberately NO `stress` CI job anymore — the app allocates over 6 GB under the simulation's concurrency and could exhaust a shared runner; `bin/stress.sh` is the developer-run path. `config.toml` is a privileged Docker runner config for GitLab.

## Stress test infrastructure
- The `stress-test` Maven profile is opt-in (never runs with plain `./mvnw install`/`verify`). Its job is only to assemble the runnable **stress jar**: `build-helper-maven-plugin` adds the `src/stress/java` source root, the profile declares `org.testcontainers:testcontainers-postgresql` as a profile-scoped (compile) dependency — named like that because Testcontainers **2.x** (managed by the Boot 4 BOM, `testcontainers.version=2.0.5`) renamed the old `org.testcontainers:postgresql` artifact; do not re-add the 1.x name or a raw `<version>` (Boot's BOM manages 2.0.5). `PostgreSQLContainer` still lives in `org.testcontainers.containers`. — and the parent-bound Boot `repackage` goal (bound to the `package` phase whenever spring-boot-maven-plugin is configured) turns `./mvnw -Pstress-test package` into a fat jar bundling the stress beans + Testcontainers. It DOES NOT start the app or run Gatling (those live in `bin/stress.sh`). Don't move the Testcontainers dep to test scope or to the global `<dependencies>`, and don't move the stress beans back into `src/main/java` (plain `./mvnw test` compiles that tree without Testcontainers on the classpath).
- Classpath isolation is the whole point: `bin/stress.sh` runs the app with `java -jar` (its JVM sees only the packaged jar — no Gatling, no test frameworks), and the simulation runs in the standalone `stress-sim/` module whose pom is deliberately ORPHANED (no parent, so it inherits none of the app's dependencies). This prevents app jars from ever leaking into the Gatling JVM — that leak is how `jasperreports-xalan`'s `xalan:2.7.3` (incomplete `TransformerFactoryImpl`, no `org.apache.xml.serializer`) used to shadow the JDK's xsltc and crash Gatling's own `java.util.prefs` boot. The module is now kept in the app jar: the app never touches `java.util.prefs`, and the isolation keeps it out of the Gatling JVM, so it is harmless — don't remove it as a "fix" for that old crash.
- Build/env: pom targets Java 25 (`java.version`) and declares `annotationProcessorPaths` in `maven-compiler-plugin` so annotation processing still works on JDK 23+ (classpath annotation processing is disabled there). Spring Boot 4.1.1's BOM manages Netty 4.2, so the old `io.netty:netty-bom` override (added because Boot 3.3.2 pinned Netty 4.1 while Gatling 3.15 needs 4.2 APIs) is GONE — do not re-add it. Kotlin is pinned via `kotlin.version`/`version.kotlin`; don't remove the `kotlin-maven-lombok` dependency (stress test sources use Lombok). `version.gatling`/`version.gatling-maven-plugin` now live ONLY in `stress-sim/pom.xml` (the root has no Gatling dependency anymore).
- Simulation: `stress-sim/src/test/kotlin/stress/JasperReportsStressSimulation.kt` — Gatling Java API from Kotlin, `randomSwitch` over the 4 fixture reports (root `emp-report.pdf`, `inner-dir/...pdf?dep_id=1`, `sub-report/...pdf?some_time=...`, `book/...pdf?some_date=...&JR_force_compile=true`), linear `rampUsers` to `stress.target.vusers` then hold. Asserts p99 < `stress.max.p99.ms` and success rates. All knobs are `-Dstress.*` system properties with defaults in `bin/stress.sh` (`STRESS_*` env-var overrides): `stress.base.url` is the only one it needs from outside. The `gatling:test` goal itself runs the module's `test-compile` phase first (its mojo declares `<executePhase>test-compile</executePhase>`), and that kotlin execution must declare an explicit `<sourceDirs>` pointing at `src/test/kotlin` — `kotlin-maven-plugin` does not auto-add it, and without it gatling fails with "No simulations to run".
- `bin/stress.sh` runs: (1) `./mvnw clean install -DskipTests` — a clean install of the web service itself (the artifact under test), (2) `./mvnw -Pstress-test package -DskipTests` — the profile jar that bundles the stress beans into the runnable fat jar, (3) `java -jar target/jasper-reports-api-*.jar --spring.profiles.active=stress-test --server.port=<STRESS_PORT>` with `-Dstress.db.latency.ms`/`-Dstress.dataset.size`, waiting until `/report/emp-report.pdf` answers 200, (4) `./mvnw -f stress-sim/pom.xml gatling:test` against `stress.base.url`. An `EXIT` trap kills the app however the script ends, so no orphan — do not regress that back to `spring-boot:start/stop` (which strands the app when a build goal fails or you Ctrl-C).
- The forked app runs the `stress-test` Spring profile: `src/main/resources/application-stress-test.properties` (reports-dir = the test fixtures, `spring.security.user.name/password=user/pass`). The backing DB is a real PostgreSQL Testcontainer. The Hikari pool (`stress.db.pool.size`, default 300) is covered by raising the container's `max_connections` (stock Postgres default is 100) — don't remove that; a pool larger than Postgres' connection limit fails under load. `stress.db.latency.ms` defaults to 0 (real Postgres latency) and only adds extra fake latency when set.
- `JdbcReportGeneratorService` always closes the JDBC connection it borrows after fill (JRFiller doesn't close connections passed in) — don't reintroduce the leak; a leaked connection saturates the pool and looks like a DB bottleneck.
- Stress-only beans live in `src/stress/java/dev/galal/jasperreports/rest/config/stress/`, both `@Profile("stress-test")` so they never activate in production: `LargeDatasetGenerator` (bulk-inserts to `stress.dataset.size` employee rows via a portable JDBC batch — avoid re-introducing H2-only SQL like `SYSTEM_RANGE`) and `ArtificialLatencyDataSource` (`@Primary`, starts the shared `PostgreSQLContainer("postgres:latest")`, points the Hikari pool at it and adds `stress.db.latency.ms` per `getConnection` when set; pool size is set directly on the `HikariDataSource` from `stress.db.pool.size`, not via `spring.datasource.hikari.*` which the bean ignores). It injects `org.springframework.boot.jdbc.autoconfigure.DataSourceProperties` — Boot 4 moved that class from `spring-boot-autoconfigure` into the new `spring-boot-jdbc` module; don't revert the import to the old `org.springframework.boot.autoconfigure.jdbc` package.
- If you edit `JdbcReportGeneratorService`'s connection handling, re-check that per-request DB latency still honors `ArtificialLatencyDataSource`.
- Plain `./mvnw test` must still pass: the stress profile/beans are inactive and `AdminApiTest`'s exact 6-fixture list is untouched.
- Don't run the stress test to verify changes, it will be done by the developer
